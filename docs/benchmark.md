# MinerU 文档解析服务压测报告

- **日期**: 2026-11-12
- **目标**: 测算 MinerU 自建解析服务的负载能力与解析速度
- **数据集**: 真实文档 180 个（153 PDF / 17 Excel / 5 docx / 5 pptx），共 325MB
- **压测样本**: 按文件大小分层抽取 27~36 个文件，各并发档使用同一样本

## 1. 环境与被测服务

| 项 | 值 |
|---|---|
| CPU | i7-10700F（16 核） |
| 内存 | 31GB（服务进程峰值占用 25.5~27.9GB） |
| GPU | RTX 2080 Ti 22GB，vLLM 后端（常驻 7.1GB 显存） |
| 服务 | MinerU 4.2.0 `api-server`，tier=advanced，服务端并发上限 32，GPU 模式 |
| 接口 | 异步任务式：POST /v1/tasks → PUT upload → 轮询 → 取结果 |

## 2. 压测结果

| 并发 | 成功/总数 | 耗时 | 文件吞吐 | 页吞吐 | 单文件延迟 p50 / p90 (服务端) | 客户端平均往返 | GPU 均值 |
|---|---|---|---|---|---|---|---|
| 1（基线） | 8/9* | 141s | 3.4 个/分 | 66.6 页/分 | 21.6s / 40.2s | 17.7s | 77% |
| 4 | 27/27 | 1407s | 1.15 个/分 | **76.9 页/分** | 110s / 302s | 203.6s | 94% |
| 8 | 27/27 | 462s | 3.51 个/分 | 78.5 页/分† | 109s / 286s | 128.4s | 96% |

\* 唯一失败为 `.xlsm`（服务不支持该格式），非负载问题。
† C8 档页数取自 /v1/usage 差值，可能少量漏计；文件吞吐与延迟数据可靠。

显存峰值 ~9.9GB / 22GB，全程无崩溃、无 OOM、无非格式类解析失败。

## 3. 结论

1. **解析速度上限 ≈ 77~80 页/分钟（约 1.3 页/秒）**。并发 1→8，页吞吐仅从 66.6 提升到 78.5 页/分（+18%），之后趋于平台化；GPU 利用率从 77% 升至 96% 即饱和。**瓶颈是 GPU 算力（2080 Ti），不是并发配置。**
2. **并发换不来吞吐，只换来排队**：并发 4 时单文件 p50 延迟从 21.6s 恶化到 ~110s（5 倍），p90 达 5 分钟。大文件（35MB 讲义 PDF）单文件最长 ~5 分钟。
3. **推荐工作并发为 2~4**：C4 已让 GPU 达 94%，再高只会拉长队列延迟；对交互式场景建议并发 1~2 以保住单文件 20~40s 的响应。
4. **容量估算**：按 77 页/分饱和吞吐折算 —— 每天 8h 满载 ≈ **3.7 万页/天**；若文档平均 30 页 ≈ 1200 个文档/天。换更大显卡（如 4090）是提升吞吐的最直接路径。
5. **兼容性**：`.xlsm` 不支持（报 "Unsupported file type"），需在接入层拦截或转存为 `.xlsx`。
6. **稳定性风险提示**：服务进程内存峰值 27.9GB / 系统共 31GB，长时间满载下余量偏小，建议监控并考虑定期重启策略。

## 4. 局限性说明

- 每档仅运行一轮，无重复试验；C16/C32 档未完成（时间所限），饱和点结论由 C1/C4/C8 三点外推，趋势一致性较强。
- 服务端按 sha256 去重文件并缓存解析结果，前几轮测试存在轻微缓存干扰（已识别并在正式轮次规避）。
- 全量 180 文件的长时间满载稳定性未验证，建议择机补测。

## 5. 复现

压测脚本（异步任务提交 + 轮询统计）未包含在本仓库，核心逻辑即按上文接口顺序调用，
延迟分位数取自服务端日志。
